# 发布与命名规则

Point Taken（中文名「懂你意思」）在 GitHub Releases 上发布 macOS 和 Windows 安装包。两个平台用同一个版本号、同一次发布；
安装包由 GitHub Actions 从打了标签的提交构建、签名、上传，不在本机手工打包上传。以下名字都由版本号推出来，不要手写别的叫法。

## 版本号

- 用语义化版本 `主版本.次版本.修订号`，如 `0.2.0`。
  - 修订号：只修 bug。
  - 次版本：加功能，旧用法不受影响。
  - 主版本：有不兼容的改动（1.0 之前可以在次版本里改）。
- 预发布在后面加 `-beta.N` / `-rc.N`，如 `0.2.0-beta.2`；带 `-` 的版本自动标成 Pre-release，不会成为「Latest」。
- **唯一来源是仓库根目录的 `VERSION` 文件**（一行，不带 `v`）。别处都不写版本号，构建时从它读：

  | 用在哪 | 怎么来的 | 例子（VERSION = `0.2.0-beta.2`） |
  | --- | --- | --- |
  | macOS `CFBundleShortVersionString` | 去掉预发布后缀（苹果只认数字） | `0.2.0` |
  | macOS `CFBundleVersion` | 提交数（`git rev-list --count HEAD`，只增不减） | `412` |
  | macOS `PointTakenVersion`（设置里显示的版本） | 完整版本 | `0.2.0-beta.2` |
  | Windows 产品版本（`Directory.Build.props`） | 完整版本 | `0.2.0-beta.2` |
  | Windows 文件版本 | 数字部分 + CI 构建号 | `0.2.0.37` |

  `app/macos/Info.plist` 里的版本是占位的 `0.0.0`，`PointTaken.App.csproj` 里没有 `<Version>`；`tests/test_release_tools.py` 会检查没人把版本号写回去。

## 各处名字

| 东西 | 规则 | 例子 |
| --- | --- | --- |
| Git 标签 | `v<版本>` | `v0.1.0`、`v0.2.0-beta.2` |
| Release 标题 | `Point Taken <版本>` | `Point Taken 0.2.0-beta.2` |
| macOS 安装包 | `PointTaken-<版本>-macos-<架构>.dmg` | `PointTaken-0.2.0-beta.2-macos-arm64.dmg` |
| Windows 安装程序 | `PointTaken-<版本>-windows-<架构>-setup.exe` | `PointTaken-0.2.0-beta.2-windows-x64-setup.exe` |
| Windows 免安装包 | `PointTaken-<版本>-windows-<架构>.zip` | `PointTaken-0.2.0-beta.2-windows-x64.zip` |
| 校验文件 | 安装包名 + `.sha256` | `PointTaken-0.2.0-beta.2-macos-arm64.dmg.sha256` |
| dmg 卷名 | `Point Taken <版本>` | 挂载后显示 `Point Taken 0.2.0-beta.2` |

- 架构写 `arm64`（Apple 芯片）、`x86_64`（Intel）或 `universal`（两者合一）；Windows 写 `x64` 或 `arm64`。现在只出 macOS `arm64` 和 Windows `x64`。
- 文件名只用英文、数字、`.` 和 `-`，不带空格和中文，方便下载链接和命令行。`.github/scripts/release.py verify` 在上传前按这张表检查。

## 发布一个版本

1. **写更新日志**：平时每个用户能感觉到的改动，都在 PR 里写进 `CHANGELOG.md` 的 `## [Unreleased]`（先中文后英文）。
2. **改版本号**：开一个 PR，
   - 把 `VERSION` 改成新版本；
   - 把 `CHANGELOG.md` 里 `## [Unreleased]` 下的内容移到新的 `## [<版本>] - <日期>` 下，Unreleased 留空；文件末尾的比较链接加一行；
   - 等 CI（Windows、macOS、Python）都通过再合并。CI 的产物里有这次的未签名安装包，可以先下下来试。
3. **打标签**（在合并后的 main 上）：

   ```bash
   git switch main && git pull
   git tag -a v0.2.0 -m "Point Taken 0.2.0"
   git push origin v0.2.0
   ```

4. **自动发布**：推送标签触发 `.github/workflows/release.yml`（Actions 页能看进度，约 15～30 分钟，公证要多几分钟）：
   1. 检查标签和 `VERSION` 一致、`CHANGELOG.md` 有这个版本的一节、这个版本还没发布过；
   2. Windows、macOS 同时构建：跑测试 → 编译 → 签名（有证书时）→ 打包 → 生成 `.sha256`；macOS 有凭据时公证并 staple；
   3. 核对文件名和校验和，生成构建来源证明（`gh attestation verify`），先建**草稿** Release 传齐全部文件，再公开。
      说明 = `CHANGELOG.md` 里这一节 + `.github/release-footer.md`（安装和校验步骤）。
5. **检查**：在 Releases 页面下载两个平台的包装一遍。

### 出错了怎么办

- **标签和 VERSION 对不上 / 没写 CHANGELOG**：工作流第一步就失败，什么都不会发布。删掉标签（`git push origin :refs/tags/v0.2.0`、`git tag -d v0.2.0`），修好后重新打。
- **构建或签名失败、想换了证书重来**：Release 还是草稿（或者根本没建）。修好原因后，在 Actions → Release → Run workflow 填同一个标签重跑（这个按钮在工作流合并进 main 之后才有），草稿里的文件会被替换。
- **只想先看草稿**：把仓库变量 `RELEASE_DRAFT_ONLY` 设成 `true`，工作流只建草稿不公开；在 Releases 页面检查后手动点 Publish。
- **已经公开的版本有问题**：不要改已发布的 Release 或移动标签（下载过的人校验会对不上）。修好后发一个新的修订号（如 `0.2.1`）。工作流拒绝覆盖已发布的 Release。

## CI

`.github/workflows/ci.yml`，每个 PR 和每次推送 main 都跑：

| 任务 | 在哪跑 | 做什么 |
| --- | --- | --- |
| Windows · build, test, package | `windows-2025` | 编译整个解决方案、`dotnet test`、打未签名的 zip 和 setup.exe（作为产物保留 7 天） |
| macOS · build, test, package | `macos-26`（Apple 芯片） | `swift test`、打 ad-hoc 签名的 dmg（产物保留 7 天） |
| Python · ubuntu / macos | `ubuntu-24.04`、`macos-26` | 用 uv 在 `scripts/.python-version` 的 Python 上跑 `tests/` |

- 运行环境写死版本（不用 `*-latest`），升级时改一处、看 CI 结果。第三方 Action 固定到提交 SHA，Dependabot 每周提一个更新 PR。
- 失败时：日志里直接有出错的测试；Windows 的测试报告（trx）作为产物上传。
- Python 测试暂时不在 Windows 上跑：有几个测试用到 Windows 没有的 POSIX 调用（`os.getpriority`），或按系统代码页（GBK）读文件，要先修测试。

### 建议的分支保护（仓库 Settings → Rules → Rulesets，作用于 `main`）

- 合并前必须通过的检查：`Windows · build, test, package`、`macOS · build, test, package`、`Python · ubuntu-24.04`、`Python · macos-26`；
- 必须经过 PR，禁止强制推送和删除分支；
- 另建一条标签规则：`v*` 标签禁止删除和移动（只允许仓库管理员创建）。

## 签名与公证

证书和密钥**只放 GitHub Secrets**（仓库 Settings → Secrets and variables → Actions），不进仓库（`.gitignore` 挡了 `*.p12`、`*.pfx`、`*.p8`）。
没配的那一项会被跳过，工作流在日志里给出黄色警告，照样出包。

### macOS：Developer ID 签名 + 公证

需要 Apple Developer Program 会员（个人 99 美元/年）。

1. 在 Mac 上用 Xcode（Settings → Accounts → Manage Certificates → `+` → Developer ID Application）或开发者网站生成 **Developer ID Application** 证书。
2. 在「钥匙串访问」里找到它，连同私钥导出为 `.p12`，设一个密码。
3. 在 [App Store Connect → 用户和访问 → 集成 → App Store Connect API](https://appstoreconnect.apple.com/access/integrations/api) 新建一个团队密钥（权限 Developer 即可），下载 `AuthKey_XXXX.p8`（只能下一次），记下 Key ID 和 Issuer ID。
4. 填 Secrets：

   | Secret | 内容 |
   | --- | --- |
   | `MACOS_CERT_P12_BASE64` | `base64 -i cert.p12 \| pbcopy` 的结果 |
   | `MACOS_CERT_PASSWORD` | 导出 .p12 时设的密码 |
   | `APPLE_API_KEY_P8_BASE64` | `base64 -i AuthKey_XXXX.p8 \| pbcopy` 的结果 |
   | `APPLE_API_KEY_ID` | Key ID（10 位） |
   | `APPLE_API_ISSUER_ID` | Issuer ID（UUID） |

工作流做的事（`app/macos/build-app.sh`、`build-dmg.sh`）：在临时钥匙串里导入证书 → App 用 hardened runtime + 时间戳 + `app/macos/PointTaken.entitlements`（麦克风）签名 → dmg 签名 → `notarytool submit --wait` → `stapler staple` → `spctl` 自检 → 删掉临时钥匙串。
本机也能这样打：`POINT_TAKEN_SIGN_IDENTITY="Developer ID Application: …" POINT_TAKEN_NOTARY_PROFILE=<notarytool store-credentials 存的名字> app/macos/build-dmg.sh`。

注意：

- 改用 Developer ID 后签名身份变了，用户升级后要在「隐私与安全性」里重新允许一次屏幕录制、麦克风和辅助功能；之后的版本都不用。
- 没公证的版本，macOS 15 起右键「打开」已经不能绕过，只能到「系统设置 → 隐私与安全性」点「仍要打开」。
- Homebrew 从 2026 年 9 月起停用不能通过 Gatekeeper 的 cask，所以要等公证之后才适合上 Homebrew（自建 tap `yanshuxiang/homebrew-tap` 或提交到官方 cask）。

### Windows：代码签名

自签名证书（0.2.0-beta.1 用过的 `CN=Point Taken`）对别人的电脑没有任何信任作用，不放进 CI；本机测试时仍可以 `build.ps1 -Sign <指纹>`。正式签名三选一：

1. **SignPath Foundation（推荐，免费）**：给开源项目的免费代码签名，要求 OSI 许可证（GPL-3.0 符合）和公开仓库，签名者显示为「SignPath Foundation」。在 [signpath.org](https://signpath.org/) 申请，项目页面要有代码签名策略和致谢（「Free code signing provided by SignPath.io, certificate by SignPath Foundation」）。
   批下来以后：
   - 在 SignPath 项目里建两个 Artifact configuration，内容照抄 `.github/signpath/windows-app.xml`（slug `windows-app`）和 `windows-installer.xml`（slug `windows-installer`）；连接 GitHub 作为 Trusted Build System；
   - Secret `SIGNPATH_API_TOKEN`；Variables `SIGNPATH_ORGANIZATION_ID`、`SIGNPATH_PROJECT_SLUG`、`SIGNPATH_POLICY_SLUG`（如 `release-signing`）。
   - 工作流先签 `PointTaken.exe` 等三个文件，再用签好的文件打安装程序，再签安装程序。
2. **Azure Artifact Signing（原 Trusted Signing，9.99 美元/月）**：目前个人开发者只开放美国和加拿大，组织开放美、加、欧盟、英国。符合条件时可以换成它（signtool + `Azure.CodeSigning.Dlib`），需要另加一个签名步骤。
3. **买 OV 代码签名证书**：2023 年起私钥必须放在硬件里，CI 一般要用 CA 的云签名服务（SSL.com eSigner、DigiCert KeyLocker、Certum SimplySign 等）。能导出 `.pfx` 的证书可以直接用：Secret `WINDOWS_CERT_PFX_BASE64`（`[Convert]::ToBase64String([IO.File]::ReadAllBytes('cert.pfx'))`）+ `WINDOWS_CERT_PASSWORD`。
   EV 证书从 2024 年起也不再一上来就消除 SmartScreen 提示，不值得为此多花钱。

签名后 SmartScreen 的信誉要随下载量慢慢积累，早期仍可能提示。

## 本机打包（不发布）

- macOS：`app/macos/build-dmg.sh` → `dist/PointTaken-<版本>-macos-<架构>.dmg`（有 Apple Development 证书时用它签，否则 ad-hoc）。
- Windows：`powershell -ExecutionPolicy Bypass -File app\windows\build.ps1` → `dist\` 下的 zip 和 setup.exe（需要 [Inno Setup 6](https://jrsoftware.org/isdl.php)；`-NoInstaller` 跳过安装程序，`-Sign <指纹>` 签名）。
- `dist/` 不进仓库。工作区不干净时打出来的包和任何提交都对不上，只能自己试用。

## 以后可以加的分发渠道

- **winget**：有受信任签名的正式版（不带 `-`）发布后，用 [wingetcreate](https://github.com/microsoft/winget-create) 给 `microsoft/winget-pkgs` 提交 `yanshuxiang.PointTaken` 的清单，安装程序用 setup.exe（Inno Setup，静默参数 `/VERYSILENT`）；之后可以在发布工作流里加一步自动提交新版本。
- **Homebrew**：公证之后，见上文。

## 说明

- 本地的 `v0.3.0`～`v1.0.22` 等标签是从上游带来的，不属于 Point Taken 的版本，不要推到 origin（所以推标签时只推那一个，不要 `git push --tags`）。
- 0.2.0-beta.1 之前（含）的版本是本机手工打包上传的；从 0.2.0-beta.2 起由发布工作流生成。
